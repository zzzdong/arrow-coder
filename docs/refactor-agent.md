从日志里可以非常清楚地看到当前实现的两个核心问题——它们直接表现为“超过最大工具调用次数（18/15）”，以及你注意到的“只有2条消息”的异常结构。

这两个问题其实是紧密关联的：

1.  **上下文构造方式完全错误，导致 LLM 无法“理解”已有信息。**
    *   **问题现象**：发给 LLM 的请求里虽然只有一个 `user` 消息，但它内部被塞进了一个巨大的、杂乱的文本块。这个文本块把“项目摘要”、“对话历史”和好几轮“迭代进度”（也就是之前工具调用的结果）粗暴地拼在了一起。
    *   **根本原因**：LLM 没有被“喂”给一个正确的、结构化的对话历史。它没有看到类似“用户提问 -> 助手请求工具 -> 工具返回结果 -> 助手再请求工具”这样的多轮对话记录。结果，LLM 完全不懂前面的探索过程，每次收到这个巨大的文本块都像在看一份乱糟糟的报告。它无法理解哪部分是最新的结果，哪部分是旧信息，所以只好不断重复调用 `list_dir` 和 `read_file` 来自己重新探索，直到工具调用次数被耗尽。

2.  **架构设计在代码实现中未对齐，混淆了“任务内历史”与“跨任务装配”。**
    *   “任务内历史”指的是在一个子 Agent 执行任务时，其内部“LLM-工具”的多轮交互记录。为了让 LLM 进行连续推理，**必须将每轮的工具调用和工具结果，以正确的 `role`（如 `assistant`（带工具调用）、`tool`）追加到上下文的 `messages` 数组里**。
    *   当前实现错误地把所有工具结果都压扁成纯文本，并拼接到同一个 `user` 消息中。这等于让 LLM 每次都要处理一个不断膨胀的“超级摘要”，而不是一个清晰的、逐步进行的对话。这完全违背了标准的 LLM Agent 交互协议。

---

### 对症下药的修复方案

解决的关键在于让 `AgentLoop` 的子 Agent 在其生命周期内，能够维护一个标准的、结构化的多轮对话上下文。

#### 1. 为子 Agent 建立正确的“任务内上下文”

`AgentLoop` 的 `run` 方法内部，不能再把上下文压扁成一个巨大的纯文本 `user` 消息。它需要维护一个本地 `Vec<Message>`，并在每次和 LLM 交互后正确地追加各类消息。

修改后的流程应该是这样：

1.  **初始化**：`SessionContextManager` 仍然负责装配初始上下文，但这次它会生成一个清晰的 `messages` 列表，例如：
    *   `[system]`: 技能指令 + 注入的项目摘要。
    *   `[user]`: 用户的原始问题（如 “improve arrow-tools”）。

2.  **进入 Agent 循环，调用 LLM**：将这个 `messages` 列表发给 LLM。

3.  **LLM 返回工具调用**：
    *   **追加 `assistant` 消息**：将 LLM 返回的、包含工具调用的原始响应消息，正确地追加到本地 `messages` 数组中。
    *   **执行工具，追加 `tool` 消息**：执行每个工具调用，并将每个工具的执行结果，以独立的 `role: "tool"` 消息追加到 `messages` 数组中。

4.  **再次调用 LLM**：将已经包含了“用户提问 -> 助手想调工具 -> 工具执行结果”的完整 `messages` 列表，再次发给 LLM。这样模型就能清晰地理解当前任务的推进过程，并决定下一步行动（是继续调工具，还是给出最终答案）。

#### 2. 上下文膨胀的应对策略

随着工具调用增多，`messages` 数组会自然变长。这就是我们需要 `max_tool_calls` 限制的原因，同时也可以采用更精细的策略：

*   **源头控制**：在像 `general-qa` 这样的技能里，我们已经明确指导 LLM “Stop after 3 tool calls max”。这能从行为上预防无限制的探索。
*   **工具结果截断**：在 `read_file` 或 `list_dir` 这些工具的实现层，可以接受一个 `max_lines` 或 `depth` 的参数。Agent 循环在遇到超大结果时，可以在消息中记录一个提示，比如“(文件过大，已截断前100行)”，而不是把整个文件内容都塞进去。
*   **必要时才压缩**：如果任务确实复杂，可以引入上下文压缩。当 `messages` 的 token 数（可以用 `tiktoken-rs` 估算）超过一个阈值（如模型窗口的 70%），就对较早的工具交互对进行摘要。但这属于高级优化，**当前我们应优先确保核心循环的正确性**。

请按以下步骤调整代码：

1.  **重构 `AgentLoop::run` 的核心循环**：

    *   在 `AgentLoop` 中，每次成功执行一个工具调用，都让计数器加1。当达到 `TaskConfig` 中的 `max_tool_calls` 时，不要直接报错，而是可以在下一条发给 LLM 的消息中追加一个 `system` 提示：“已达到最大工具调用次数，请根据已有信息直接回答用户”，给任务一个优雅结束的机会。

完成这些修改后，你再试一次 “improve arrow-tools”，日志里应该能看到 LLM 沿着清晰的结构化对话进行推理，并在很少的步骤内给出最终回答。
